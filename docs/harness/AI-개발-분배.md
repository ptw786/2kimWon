# 안심온 개발 분배 — 사람과 AI가 각각 무엇을 하나

> 원칙 세 가지
> 1. **쓴 쪽과 검토하는 쪽은 다르다.** 구현한 에이전트가 자기 결과를 승인하지 않는다.
> 2. **판단은 지휘자가, 결정은 사람이.** 제안서·규칙·디자인처럼 공모전 내용이 바뀌는 것은 팀이 정한다.
> 3. **증거 없는 "완료"는 없다.** 테스트 결과·스크린샷·스모크 기록을 남긴다.

## 1. 역할

| 역할 | 누가 | 하는 일 |
|---|---|---|
| 결정자 | 팀(민세·예인·태원) + 튜터 | 기능 범위, 판정 규칙 값, 디자인 승인, GitHub 반영 |
| 지휘자 | Claude Code 메인 세션 | 작업 카드 작성, 에이전트 배정, 통합·화면 확인, 보고 |
| 구현자 | `.claude/agents/`의 역할 에이전트 | 작업 카드 하나 = 폴더 하나. 서로 다른 폴더면 병렬 |
| 검토자 | 구현과 다른 에이전트(code-reviewer · verifier) | 버그 · 계약 위반 · 규약 · 빠진 테스트 · 접근성 |

## 2. 역할 에이전트 (`.claude/agents/`)

| 에이전트 | 맡는 폴더 | 기능 |
|---|---|---|
| `api-engineer` | `apps/api` (domain 제외 판정 값) | F0 · F1 · F6 |
| `ai-engineer` | `apps/api/app/domain` · `services` · `prompts` | F3 · F4 · F5 · F11 |
| `web-frontend` | `apps/web` | F7 · F8 · F10 |
| `app-frontend` | `apps/app` | F2 · F8 · F9 |
| `designer` | `packages/design` · `docs/디자인.md` | 시안 · 토큰 |
| `evaluator` | `docs/평가` · 평가 세트 | 분류 정확도 · 민감도 |
| `proposal-writer` | 제안서 원고 · 발표 대본 | 제출 서류 |

## 3. 작업 한 건의 흐름

```
① 작업 카드 (지휘자)    기능 ID · 목표 · 손댈 폴더 · 수용 기준(구현-계획 P0 열) · 안 건드릴 것
② 계약 먼저 (필요 시)    packages/contracts/CONTRACT.md 수정
③ 구현 (역할 에이전트)   코드 + 테스트 + (화면이면) 스크린샷
④ 자체 검사             scripts/test-all.sh
⑤ 검토 (다른 에이전트)   지적마다 반영 / 반영 안 함(이유) / 팀에 질문
⑥ 통합 확인 (지휘자)     세 서버 띄우고 통합 시나리오 1회
⑦ 보고 → 팀 결정 → GitHub
```

판정 규칙(`domain/`)을 바꿀 때는 ⑤ 전에 `evaluator`가 반례를 만들고, 그 사례를 테스트로 넣는다.
